# Create custom contract sheet – alignment

## Your questions, answered

### 1. “We need to set the installment dates for each plan right? Where does that happen?”

**Where it happens:** Installment timing is set in **Admin → Payment Plans**, not in the Create custom contract sheet.

- Each **payment plan** has **Payment plan installments** (e.g. “Instalment 1”, “Instalment 2”).
- For each installment you set either:
  - **Due date offset (days)** – e.g. `0`, `30`, `60` = days after the contract start date, or  
  - **Due date** – a fixed date.
- You also set **amount type** (percentage or fixed) and **amount value**.

So the **rules** for “when is each instalment due” live on the **plan**. When a contract uses that plan, the system:

- Takes the contract’s **start date** and **weeks** (and weekly price) to get total contract value.
- Uses the plan’s installments (offsets or fixed dates) to build the actual schedule (e.g. “Instalment 1: 0 days after start”, “Instalment 2: 30 days after start”).
- Optionally writes rows into **contract_payment_schedule** (e.g. via backfill) so reports and manual payments have concrete due dates.

**In the Create custom contract sheet:** You only **choose which existing plans** to attach to the new contract (and their display order). You do **not** set installment dates there; those come from the plan configuration in Payment Plans. So:

- **Recommendation:** No change needed in the sheet for “setting” installment dates. If staff need to create a **new** plan with custom dates, they do that in **Admin → Payment Plans** first, then pick it when creating the custom contract. Optionally add a short note in the sheet: “Installment due dates are set in Admin → Payment Plans for each plan.”

### 2. “Remove scroll on the sheet, replace with progress bar at the top”

**Recommendation:** Use a **step-based** form with a **progress bar at the top** and **no scroll** (each step fits in view).

- **Progress bar:** At the very top of the sheet/drawer, show a thin bar (e.g. “Step 1 of 3”, “Step 2 of 3”, “Step 3 of 3”) so staff see where they are.
- **Steps (example):**
  - **Step 1 – Contract & dates:** Academic year, studio grade, contract name, start date, end date, and a **read-only “Weeks”** (see below).
  - **Step 2 – Pricing:** Weekly price (£), Deposit (£).
  - **Step 3 – Payment plans:** Select plans and order; staff-only note; Cancel / Create & use contract.
- Only one step is visible at a time; Next/Back or step indicators move between steps. That keeps content short enough to avoid scroll and gives a clear “progress” feel.

Alternative (weaker): Keep one long form and add a **completion** progress bar (e.g. “60% complete” from required fields). You’d still likely need scroll. So the **step-based + progress bar** approach is the one that cleanly “replaces scroll with progress bar”.

---

### 3. “Where is the number of weeks field or is it autogenerated from start and end date?”

**Current behaviour:** The number of weeks is **not** a separate input; it is **derived** from start and end date.

- In code we have `calculateWeeks(contract_start, contract_end)` and we send `weeks` in the create payload.
- So **weeks is autogenerated** from the two dates.

**Recommendation:** Keep it derived, but **show it** so staff can confirm (e.g. “21 weeks”) and so it’s clear how revenue is calculated.

- In **Step 1**, under the end date, add a **read-only line**: e.g. “Duration: **21 weeks**” (or “— weeks” if dates are missing/invalid).
- No second input; single source of truth remains start + end date.

---

### 4. “In order to calculate contract revenue right?”

**Yes.** Contract revenue (total contract value) is:

- **Total rent** = `weeks × weekly_price_override`
- **Deposit** = `deposit_override`
- **Total contract value** = total rent + deposit (conceptually: what the student pays in total; deposit + instalments cover that).

Payment plans then define **how** that value is collected (deposit due when, then instalments by due date offset or fixed date from the plan). So:

- The **Create custom contract** form gives everything needed for **contract** revenue: weeks (from dates), weekly price, deposit, and which plans apply.
- **When** each instalment is due comes from the **plan** (Payment Plans admin), not from this sheet.

No extra field is needed for revenue; showing **weeks** (read-only) just makes the link to “weeks × weekly price” obvious.

## Summary table

| Topic | Where it lives | Recommendation |
|-------|----------------|----------------|
| Installment **dates** (when each instalment is due) | **Admin → Payment Plans** (per plan: due_date_offset_days or due_date) | No change in Create custom contract sheet; optionally add a one-line note that dates are set in Payment Plans. |
| Number of **weeks** | Derived from contract start + end date | Keep derived; show read-only “Duration: X weeks” in the sheet (e.g. Step 1). |
| Contract **revenue** | weeks × weekly_price + deposit; plans define how it’s split | Current fields are sufficient; read-only weeks improves clarity. |
| Scroll vs progress bar | Create custom contract sheet UX | Replace scroll with **step-based form** (e.g. 3 steps) and a **progress bar at the top** (“Step 1 of 3”, etc.). |

---

## Suggested implementation order

1. **Add read-only “Weeks”** in the Create custom contract sheet (under end date), computed from start/end.
2. **Convert the sheet to steps** (e.g. 3 steps) with a **progress bar at the top** and **no scroll** (only one step visible at a time).
3. **Optional:** Short note in the payment plans step: “Installment due dates are set in Admin → Payment Plans for each plan.”

After that, the sheet will be aligned with: no scroll, progress at the top, weeks visible and used for revenue, and clarity that installment dates are set in Payment Plans.
